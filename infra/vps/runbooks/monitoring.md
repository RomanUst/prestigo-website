# Monitoring & Alerting Runbook (Phase 76 plan 06)

## Architecture (D-01/D-02)

Every primary alert signal comes from **outside the VPS**. If the VPS itself
goes dark, nothing here depends on it to notice — that is the entire point.

```
UptimeRobot (external SaaS) ──polls──> chat.rideprestigo.com/api
                             ──polls──> crm.rideprestigo.com/
                             │
Healthchecks.io (external SaaS) <──pings── infra/vps/scripts/backup.sh (nightly)
                                <──pings── infra/vps/scripts/monitor.sh (every 5 min,
                                            prestigo-monitor.timer)
                             │
                             └──alerts──> owner Telegram (bot integration)
                                          owner email
```

- **UptimeRobot** is the *primary* signal for "is the app reachable at all"
  (D-01). It runs entirely off the VPS — nothing installed here, nothing
  that dies with the host.
- **Healthchecks.io** is a *dead-man's switch*: the VPS pings it to say
  "I'm alive and this specific thing is healthy." A missing ping (VPS down,
  cron/timer dead, network partition) is itself the alert — no separate
  "is the monitor up" check needed.
- **Telegram + email** are UptimeRobot's and Healthchecks.io's own built-in
  integrations (D-02). No custom bot code exists anywhere in this repo for
  monitoring alerts, and `lib/content/telegram.ts` (the site's
  content-approval bot) is completely untouched — a different bot, a
  different purpose, never reused here.
- **Nothing on the VPS is the primary signal.** The on-VPS checks
  (`monitor.sh`) exist because some things — disk %, Sidekiq's own Redis
  heartbeat, TLS cert file expiry — are only observable from inside the
  host. They still report outward, through Healthchecks.io, never through
  anything that lives only on the VPS.

## Monitor & Check Inventory

| Name | What it proves | Interval | Alert condition | Source |
|---|---|---|---|---|
| Chatwoot app (chat.rideprestigo.com/api) | Chatwoot's Rails app is up **and** both its Postgres and Redis connections are healthy — not just that Caddy answers | 5 min | UptimeRobot keyword `"queue_services":"ok","data_services":"ok"` missing from the response body | UptimeRobot |
| EspoCRM login (crm.rideprestigo.com) | EspoCRM's app shell actually renders the login page — not a Caddy error page | 5 min | UptimeRobot keyword `<title>EspoCRM</title>` missing from the response body | UptimeRobot |
| prestigo-backup | The nightly restic→B2 backup ran and succeeded | pinged nightly, ~26h before alert (24h timeout + 2h grace) | Missing ping, or `backup.sh` posts to `/fail` | Healthchecks.io, pinged by `backup.sh` |
| prestigo-disk-mem | Root filesystem, RAM, and swap usage are under threshold | pinged every 5 min | disk >85%, used RAM >90%, or swap >50% (overridable via `DISK_MAX_PCT`/`MEM_MAX_PCT`/`SWAP_MAX_PCT`) | Healthchecks.io, pinged by `monitor.sh` |
| prestigo-kvm4-trigger | 7-day rolling average used-RAM stays under the KVM 4 upgrade threshold | pinged every 5 min | 7-day avg used RAM >80% (`KVM4_AVG_PCT`) | Healthchecks.io, pinged by `monitor.sh` |
| prestigo-sidekiq | Chatwoot's Sidekiq worker process is alive | pinged every 5 min | newest heartbeat (`beat` field on the Redis `processes` set) older than 60s, or the set is empty/unreadable | Healthchecks.io, pinged by `monitor.sh` |
| prestigo-espocrm-internals | EspoCRM's daemon container is running and MariaDB is healthy | pinged every 5 min | `espocrm-daemon-1` not `running`, or `healthcheck.sh --connect --innodb_initialized` fails | Healthchecks.io, pinged by `monitor.sh` |
| prestigo-tls-expiry | TLS certs for both apps have enough runway | pinged every 5 min | either cert expires within 14 days (`TLS_MIN_DAYS`) or can't be fetched | Healthchecks.io, pinged by `monitor.sh` |

Monitor/check definitions are versioned in `infra/vps/monitoring/monitors.json`
and (re-)provisioned by `infra/vps/scripts/provision-monitors.sh` — see that
script's header and this plan's Task 1/2 for the owner-account setup and
provisioning procedure. `monitor.sh`'s ping URLs live in
`/etc/prestigo/monitor.env` (root, mode 600), generated by
`provision-monitors.sh` and installed via
`ssh prestigo-vps 'sudo install -m 600 -o root -g root /dev/stdin /etc/prestigo/monitor.env'`.
`backup.sh`'s `HC_PING_BACKUP` is read from the same file (it already sources
`/etc/prestigo/monitor.env` opportunistically — no change needed there when
the file first appears).

## Alert Response Playbook

For every alert below: the Telegram message (or email) names which monitor
fired. Start there.

### "Chatwoot app" or "EspoCRM login" down (UptimeRobot)

1. `ssh prestigo-vps 'bash /opt/prestigo/scripts/smoke.sh'` — this pinpoints
   which container/check actually failed (container state, app-health body,
   auth-enforced check, cert expiry) in one command.
2. If a container is down/restarting: `docker compose -f
   /opt/prestigo/<chatwoot|espocrm>/compose.yml ps`, then check
   `docker logs <container> --since 15m` for the failing service.
3. If it's a genuine outage (not a false positive): follow
   `infra/vps/runbooks/app-deploy.md`'s restart/redeploy guidance. If the
   fix requires an app-version rollback, use `infra/vps/runbooks/upgrade.md`'s
   rollback path.
4. Once fixed, `smoke.sh` should print only `OK` lines; UptimeRobot re-checks
   every 5 minutes and clears the alert automatically.

### "prestigo-backup" missed (Healthchecks.io)

1. `ssh prestigo-vps 'systemctl status prestigo-backup.service prestigo-backup.timer'`
   — confirm the timer is still enabled/active and see the last run's exit
   code.
2. `ssh prestigo-vps 'journalctl -u prestigo-backup.service --since "yesterday"'`
   for the failure detail — `backup.sh`'s `on_err` trap logs the exact step
   that failed (`dump-chatwoot`, `snapshot`, `prune`, etc.) before pinging
   `/fail`.
3. Fix the underlying cause (disk full, B2 credentials rotated, restic repo
   lock stuck), then run `ssh prestigo-vps 'sudo /opt/prestigo/scripts/backup.sh'`
   manually to confirm a clean run and clear the check.
4. See `infra/vps/runbooks/backup-restore.md` for the full backup
   architecture and manual operator commands.

### "prestigo-disk-mem" failing (Healthchecks.io)

1. `ssh prestigo-vps 'df -h /; free -h'` to see which resource is over
   threshold.
2. Disk: find what grew — `docker system df`, old dump files under
   `/var/backups/prestigo/dumps`, or log growth under `/var/log`. Clear or
   prune (`docker system prune` is safe for dangling images/build cache
   only — never prune volumes without checking `docker volume ls` first,
   per Pitfall 15's "backup-first" rule for anything destructive).
3. Memory/swap: check `docker stats --no-stream` for the heaviest
   container. If it's consistently Sidekiq or MariaDB, this may be an early
   sign the KVM 4 upgrade trigger (below) is close — check
   `prestigo-kvm4-trigger`'s status too.

### "prestigo-kvm4-trigger" failing (Healthchecks.io) — see "KVM 4 Upgrade Triggers" below.

### "prestigo-sidekiq" failing (Healthchecks.io)

1. `ssh prestigo-vps 'docker inspect --format "{{.State.Status}} restarts={{.RestartCount}}" chatwoot-sidekiq-1'`
2. `ssh prestigo-vps 'docker logs chatwoot-sidekiq-1 --since 15m'` — look for
   a crash loop, an OOM kill (`dmesg | grep -i oom`), or a Redis connection
   error.
3. `docker compose -f /opt/prestigo/chatwoot/compose.yml restart sidekiq`
   if it's simply wedged; investigate root cause (memory pressure, a queue
   backup) before assuming a restart alone fixes it for good.

### "prestigo-espocrm-internals" failing (Healthchecks.io)

1. `ssh prestigo-vps 'docker inspect --format "{{.State.Status}}" espocrm-daemon-1'`
   and `docker logs espocrm-daemon-1 --since 15m` if it's not `running`.
2. `ssh prestigo-vps 'docker exec espocrm-db-1 healthcheck.sh --connect --innodb_initialized; echo $?'`
   to reproduce the exact failing check by hand.
3. Restart the failing service (`docker compose -f
   /opt/prestigo/espocrm/compose.yml restart <daemon|db>`) and re-run the
   check above to confirm recovery before considering it resolved.

### "prestigo-tls-expiry" failing (Healthchecks.io)

1. This should not happen under normal operation — Caddy auto-renews Let's
   Encrypt certs well before 14 days out. A failure means either a genuine
   renewal problem or the domain is unreachable from the VPS's own
   perspective.
2. `ssh prestigo-vps 'docker logs caddy-caddy-1 --since 24h | grep -i acme'`
   for renewal errors (rate-limited, DNS/HTTP-01 challenge failing, expired
   Hostinger DNS record).
3. Confirm the `chat`/`crm` A records still point at this VPS's IP (D-20) —
   an accidental DNS change is the most common cause of a renewal failure.
4. `ssh prestigo-vps 'docker compose -f /opt/prestigo/caddy/compose.yml restart caddy'`
   after fixing DNS/network, then re-run `smoke.sh`'s cert-expiry checks.

## KVM 4 Upgrade Triggers (D-11, D-12)

The plan started on **Hostinger KVM 2** (8 GB RAM / 2 vCPU), an explicit,
documented owner decision (D-11) with two independent triggers for
upgrading — either one is sufficient on its own:

1. **Automated:** `prestigo-kvm4-trigger`'s 7-day rolling average used RAM
   exceeds 80% (`KVM4_AVG_PCT`, `monitor.sh`'s `kvm4_trigger` check,
   `/var/log/prestigo/mem-usage.log`).
2. **Manual:** **a second operator is onboarded.** Operator headcount is
   not machine-observable in Phase 76 — this is a judgment call the owner
   makes, not something any script checks. Revisit whether this can become
   automated once Phase 77+ introduces multi-agent Chatwoot usage.

**Upgrade procedure (in-panel, no migration, D-11):**

1. Hostinger panel → VPS → Plan → upgrade KVM 2 → KVM 4. This is an
   in-place resize, not a new host — no DNS, backup, or app changes needed.
2. After the resize completes and the host reboots, raise each container's
   `mem_limit` in the relevant `compose.yml` (D-12 — the KVM 2 values are
   deliberately conservative; KVM 4's extra headroom should go primarily to
   Sidekiq concurrency and Postgres/MariaDB buffer settings, not sit idle).
3. Re-run `smoke.sh` to confirm all containers restart healthy under the
   new limits.
4. Record the upgrade (date, trigger reason, before/after `mem_limit`
   table) in `infra/vps/runbooks/upgrade.md`'s upgrade-log table.

## Pausing Monitors for Planned Maintenance

Before any planned downtime (app upgrade per `upgrade.md`, host reboot,
Docker Engine upgrade):

1. **UptimeRobot:** pause both monitors via the dashboard (Monitors → select
   → Pause), or `POST https://api.uptimerobot.com/v2/editMonitor` with
   `status=0`. Resume the same way (`status=1`) once the maintenance window
   ends.
2. **Healthchecks.io:** for a check whose grace period would otherwise
   expire during the maintenance window (`prestigo-disk-mem`,
   `prestigo-sidekiq`, `prestigo-espocrm-internals`, `prestigo-tls-expiry` —
   any 5-minute-interval check, effectively always during a maintenance
   window longer than ~15 minutes), pause it from the dashboard or leave
   `monitor.sh`'s timer running with `--only` scoped to skip the affected
   check for the duration; either way, resume/unpause before ending the
   session so a real post-maintenance failure isn't silently missed.
3. Never pause `prestigo-backup` — a maintenance window is exactly when you
   most want the dead-man's switch still watching.

## Re-provisioning From `monitors.json`

`infra/vps/monitoring/monitors.json` is the single source of truth for every
monitor/check definition. To re-provision after a monitor definition change
(new check, changed threshold, renamed monitor) or onto a fresh SaaS account:

```bash
UPTIMEROBOT_API_KEY=... HEALTHCHECKS_API_KEY=... \
  bash infra/vps/scripts/provision-monitors.sh
```

This is idempotent — re-running it against an already-provisioned account
creates nothing new (`created=0` for both sections). Renaming a monitor in
`monitors.json` creates a *new* monitor/check rather than renaming the live
one (provisioning matches by name) — rename deliberately, and clean up the
old entry manually in the dashboard if it's genuinely retired.

`bash infra/vps/scripts/provision-monitors.sh --status` prints one line per
monitor/check with its current live state, without creating anything.
