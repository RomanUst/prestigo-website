<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internet -> Chatwoot /webhooks/whatsapp/<public number> | anyone can POST; only a valid signature proves Meta sent it |
| owner Mac (admin token) -> Chatwoot inbox API | reads and replaces provider_config (token + app secret) |
| owner terminal -> Graph /register | carries the two-step PIN |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-78-26 | Spoofing | forged inbound WhatsApp webhooks on the manual channel | high | mitigate | --harden sets provider_config.app_secret; --probe proves unsigned 401 / wrong 401 / signed 200; re-run after credential changes (runbook) |
| T-78-27 | Information Disclosure | provider_config values (token, app secret) in output or error echoes | high | mitigate | booleans-only output contract; client redaction of provider_config keys; distinctive-value tests |
| T-78-28 | Denial of Service | PATCH replacing provider_config and dropping api_key/phone_number_id | high | mitigate | full-hash merge in memory; post-PATCH preservation checks exit 1; dry-run mode |
| T-78-29 | Tampering | probe traffic creating fake conversations in the live inbox | medium | mitigate | metadata-only payload (test asserts no messages/statuses keys) |
| T-78-30 | Information Disclosure | PIN captured via argv, pipe, logs or files | high | mitigate | no PIN argument; TTY-only hidden prompt; never printed or stored; one register call per run |
| T-78-31 | Information Disclosure | Chatwoot/Meta token sent to the webhook endpoint or a redirect target | medium | mitigate | probes use plain fetch without auth headers; redirect: 'error' everywhere |
| T-78-SC | Tampering | npm/pip/cargo installs | high | mitigate | Node built-ins only (fetch, crypto, readline); no package installs; package-legitimacy gate not triggered |
</threat_model>
