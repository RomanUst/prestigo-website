Harness rules:
- Chatwoot emitter: on every contact create/update the fake's onWrite builds a contact_updated payload from the stored contact (custom_attributes included) with changed_attributes from the diff, signs it with a fake secret (X-Chatwoot-Signature / Timestamp / Delivery) and queues a POST to the Chatwoot route.
- EspoCRM emitter: a fetch wrapper around the fake observes successful PUT/POST to /Contact; when the API key's user is not prestigo-sync (skipOwn) it queues a signed batch `[{ id, <changed attributes> }]` to the EspoCRM route; in the forced-loop scenario it emits for every writer.
- Runner: repeat { deliver queued webhook POSTs; dispatch every due outbox key; advance the clock (31 s per tick, 5 s in the forced-loop scenario) } until both queues are empty or 200 iterations (the forced-loop scenario asserts it stopped well before that).
- Tripwire client: `{ from(table), rpc(name, args), auth }` where from records 'bookings' / 'customer_profiles' (any operation), auth access records a violation, rpc records any name outside the inbound allowlist (webhook_*, chat_*, outbox_*, identity_chat_lookup, identity_by_chatwoot_contact, identity_resolve_chat, identity_attach_chat_contact, identity_phone_usable, identity_person, identity_set_espo_contact, identity_set_chatwoot_contact) and otherwise answers canned shapes; `vi.mock('@/lib/supabase', ...)` returns it from createSupabaseServiceClient.
