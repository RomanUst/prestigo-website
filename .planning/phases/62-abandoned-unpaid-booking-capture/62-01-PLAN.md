<assumption_delta_decision>
## Core assumption change (record — advisory)

**Before this phase:** a booking existed ONLY after a successful payment — a single
lifecycle anchor (`payment_intent_id`, one confirmed row inserted by the webhook).

**After this phase:** a booking exists PRE-payment in an `unpaid` state, and the stable
identity of a checkout ATTEMPT becomes `attempt_id` (promoted in 62-02) because both
`payment_intent_id` and `booking_reference` are regenerated on every retry/currency
toggle (verified in RESEARCH Pitfall 3).

**Decision:** PROMOTE `attempt_id` as the dedup/reconciliation anchor for the
unpaid→confirmed lifecycle (wired in 62-02). `payment_intent_id` remains the Stripe-side
idempotency key for the SUCCEEDED webhook. Consistency invariant: the row's
`payment_intent_id` must always reflect the CURRENT PaymentIntent (rewritten on each
retry-side UPSERT) so the webhook can still locate the row by the winning PI. In THIS
tracer plan there is no retry, so the one-way capture keys on `(payment_intent_id, leg)`;
62-02 switches the capture key to `(attempt_id, leg)` — a functionality fill, not an
architectural change to the capture→reconcile flow.

**Suggested invariant test (optional, added in 62-02):** a paid attempt reconciles to
exactly one confirmed row and fires each side-effect once, for one-way and round-trip.
</assumption_delta_decision>
