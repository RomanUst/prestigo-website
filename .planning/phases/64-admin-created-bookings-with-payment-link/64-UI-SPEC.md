# Phase 64 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — this project's admin surface is a mature, established **custom CSS-custom-property + inline `React.CSSProperties` design system**, not shadcn/Tailwind component classes. `components.json` does not exist; no admin component under `components/admin/**` uses shadcn/Radix primitives. Initializing shadcn now would fork the design language mid-surface, inside the exact `ManualBookingForm.tsx` and `BookingsTable.tsx` components this phase extends — rejected, same conclusion Phase 63 already reached for this admin surface. |
| Preset | not applicable |
| Component library | none (hand-rolled inline-style components) |
| Icon library | `lucide-react` — already used in `ManualBookingForm.tsx` (`X`, `Calculator`); this phase adds `Copy` and `Send` (or `RefreshCw`) from the same package, no new dependency |
| Font | `var(--font-montserrat)` → Inter, for all UI/body/labels/inputs/buttons; `var(--font-cormorant)` → Fraunces, for the modal heading only |

**Rationale for declining the shadcn gate:** Phase 64 is almost entirely a composition phase per 64-RESEARCH.md — ANEW-01/ANEW-05 are already implemented, and the genuinely new surface (payment-collection toggle, payment-link result panel, row-level "Generate payment link" action) extends `ManualBookingForm.tsx` and `BookingsTable.tsx` using the exact inline-style idioms those files already ship (`labelStyle`/`inputStyle`/`sectionLabelStyle` from `ManualBookingForm.tsx`; the icon-button convention from its own Calculator/Check buttons; the assign-button convention from `DriverAssignmentSection.tsx`). No new npm package is required beyond two more `lucide-react` icons already in the installed package. Introducing shadcn here would visually and structurally fork this one admin surface from the other 20+ admin components sharing the same navy/gold inline-style language.

## Visual Hierarchy

Before save, the primary anchor is the **"Collect payment via link"** toggle inside a new "PAYMENT" section (placed after "PASSENGER DETAILS", before the footer buttons) — it is the one control that changes what the primary CTA does (D-03). After a successful create-with-payment (or a D-05 row-level "Generate Payment Link" action), the **payment-link result panel** — URL + Copy + Resend, with the EUR amount in copper — becomes the single dominant focal point of its context (the modal, or the expanded row), exactly mirroring how Phase 63's price-review step became the row's focal point once triggered.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0F1D2C` (`var(--anthracite)`) | Modal/page/table background, plain input backgrounds |
| Secondary (30%) | `#17293B` (`var(--anthracite-mid)`) | Modal background, payment-link-result panel background, expanded-row panel background |
| Accent (10%) | `#BFA06A` (`var(--copper)`) — labels use `#D4BB86` (`var(--copper-light)`) for AA contrast on navy | See "Accent reserved for" below |
| Destructive | `#f87171` | Validation/error text only: link-generation failure, resend failure, existing form-level error banner |

Accent (`--copper` / `--copper-light`) reserved for — explicit list, nothing else may use it:
- The **"PAYMENT"** section label (11px uppercase, `var(--copper-light)`) — same section-label convention as "TRIP DETAILS"/"PASSENGER DETAILS" in `ManualBookingForm.tsx`
- **Copy Link** and **Resend Email** icon buttons — border `var(--anthracite-light)`, icon color `var(--copper)`, reusing the exact existing Calculator/flight-Check icon-button style from `ManualBookingForm.tsx` verbatim (never a filled copper background on these)
- The row-level **"Generate Payment Link"** button — border `var(--copper)`, transparent background, filling to solid copper on hover with `var(--anthracite)` text, identical to `DriverAssignmentSection.tsx`'s existing "Assign" button convention
- The payment-link-result panel's **left accent line/border** (`border-left: 3px solid var(--copper)`, mirroring the existing "Copper accent line" convention used at the top of the `ManualBookingForm` modal and the booking-reference box pattern in `lib/email.ts`)
- The **EUR amount** shown inside the payment-link-result panel (primary currency figure, mirrors the existing driver-price/hourly-strip-price copper-emphasis convention)
- The email's **"Pay Now"** CTA button (border `#BFA06A`, color `#BFA06A`, transparent — the exact `buildDriverAssignmentHtml` single-CTA-button pattern cited in 64-RESEARCH.md, reused verbatim, single button only — not the accept/decline pair)

Existing `StatusBadge` semantic palette (locked, reuse verbatim, no new status colors added): `unpaid` `#f59e0b` is the one this phase's payment-link bookings land in (D-01) — already shipped, unchanged.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (collect-payment path) | **"Create & Send Payment Link"** — `ManualBookingForm`'s submit button label when "Collect payment via link" is checked (replaces the generic "Create Booking" only in this state, per D-03: generate + email in the same action). |
| Primary CTA (no-payment path, unchanged) | **"Create Booking"** — kept verbatim when the toggle is unchecked (ANEW-05 path, no Stripe interaction). |
| Collect-payment toggle label | **"Collect payment via link"** — helper text: **"Generates a Stripe payment link and emails it to the client immediately. The link never expires and can be resent anytime."** (D-01/D-03/D-04) |
| Booking-status choice (shown only when the toggle above is OFF) | Label **"Booking status"**, options **"Confirmed — paid offline (cash/invoice)"** (default, per D-02) and **"Pending"**. |
| Row-level action (D-05) | **"Generate Payment Link"** — new button in `BookingsTable.tsx`'s expanded row, shown only for `unpaid`/`pending` bookings that have no `payment_link_url` yet. |
| Late-attach status notice | **"Generating a payment link will mark this booking as Unpaid until the client pays."** — helper line under the D-05 row action, shown specifically when the target booking is currently `pending` (communicates the Pitfall-2 status flip before the operator clicks). |
| Round-trip linked-leg notice (D-05 only — see UI Considerations) | **"This link also covers the linked return/outbound leg — paying once settles both."** — shown in the result panel only when a sibling unpaid leg was found and included in the link's metadata; never shown from the create flow (round-trip isn't creatable there — 64-RESEARCH.md Pitfall 3). |
| Payment-link result panel heading | **"Payment link ready"** |
| Payment-link result panel body | **"Already emailed to {client email}. Copy the link to share it another way (e.g. WhatsApp), or resend the email."** |
| Copy action | **"Copy Link"** → on success, inline **"Copied!"** for 2s (matches the existing 2000ms feedback-timeout convention in `NotificationToggles.tsx`); on an unsupported-clipboard fallback, the link text is auto-selected so the operator can copy manually — never a silent no-op. |
| Resend action | **"Resend Email"** → in-flight **"Sending..."** (disabled) → success **"Sent"** (2s, same feedback pattern) → failure **"Failed to send — try again"** (`#f87171`, same shape as `DriverAssignmentSection`'s error copy). Per D-07, resend has its own code path and is never blocked by the initial-send `logEmail` dedup window. |
| Empty state heading | **"No payment link yet."** — shown inside the row-level payment section (D-05 context) before the operator has generated one. |
| Empty state body | **"Generate one to let the client pay online."** |
| Error state | **"Booking was created, but the payment link could not be generated — use \"Generate Payment Link\" from the bookings list to retry."** (create-flow: booking insert and link generation are not atomic — the booking always persists even if the Stripe call fails) · **"Could not generate payment link. Please try again."** (D-05 row action failure, identical tone/shape to `DriverAssignmentSection.tsx`'s existing "Could not assign driver. Please try again.") |
| Destructive confirmation | Not applicable this phase — no new destructive action is introduced (refunds/re-charging are explicitly out of scope per REQUIREMENTS.md; the pre-existing "Cancel Booking" modal is unchanged and out of scope here). |

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5) and lifted by plan-phase's
> `## UI Considerations` lift rule via the identical rule as SPEC `## Edge Coverage`. Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).
> Empty-state and error-state COPY live in `## Copywriting Contract` above — this section covers
> state coverage and REFERENCES those rows rather than restating the copy (de-dup).

Elements classified against the 8-category taxonomy (element kinds in brackets): E1 collect-payment toggle + status choice in `ManualBookingForm` [form, interactive-control], E2 payment-link result panel — URL + Copy + Resend, appearing in both the create-flow modal and the `BookingsTable` expanded row [interactive-control, static-content], E3 `BookingsTable` row-level "Generate Payment Link" action, pre-link state [interactive-control], E4 payment-request email template [static-content].

Resolution: **11 covered, 0 backstop, 3 dismissed** across the 14 applicable considerations (categories not applicable to an element's kind — e.g. `populated`/`zero-one-many` for non-collection elements — are excluded per the taxonomy's relevance filter, not silently dropped).

| Element | Category | Status | Resolution / Reason |
|---------|----------|--------|---------------------|
| E1 toggle + status choice | empty | ✅ covered | Form defaults: "Collect payment via link" unchecked (operator opts in); when unchecked, "Booking status" defaults to **Confirmed** per D-02. |
| E1 toggle + status choice | loading | ✅ covered | Submit button shows a disabled loading label — **"Creating..."** (no link) or **"Creating & Sending Link..."** (link path) — while the POST is in flight, same disabled/opacity treatment as the existing submit state. |
| E1 toggle + status choice | error | ✅ covered | See Copywriting Contract "Error state" (create-flow row) — booking creation and Stripe link generation are explicitly non-atomic; the UI must not imply the booking failed when only the link step did. |

| E1 toggle + status choice | long-text | ✅ covered | Toggle helper text and status-option labels are short, fixed strings, not user-generated — no wrap/truncation concern; deduped against the form's existing long-text handling for its other fields (unchanged). |
| E2 payment-link result panel | loading | ✅ covered | While the link is being generated (both the create-flow panel and the D-05 row-action panel), a muted **"Generating link…"** line (11px, `var(--warmgrey)`) replaces the URL/Copy/Resend controls. |

| E2 payment-link result panel | long-text | ✅ covered | Same rule as overflow above — deduped, one resolution covers both categories for this element. |

| E4 payment-request email | overflow | ✅ covered | Trip-summary table cells (route, date/time, vehicle class) wrap rather than truncate, reusing the exact no-truncation convention already established across every existing branded email's "TRIP DETAILS" table (`buildDriverAssignmentHtml`, `buildStatusEmailHtml`). |
| E4 payment-request email | long-text | ✅ covered | Same rule as overflow above — deduped, one resolution covers both categories for this element. |
