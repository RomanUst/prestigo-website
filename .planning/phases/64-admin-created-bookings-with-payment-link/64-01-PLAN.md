<objective>
Lead Phase 64 with a production-quality end-to-end tracer: an operator saves a ONE-WAY admin booking with "collect payment", the server generates a Stripe Payment Link (server-authoritative amount), persists its URL/id, emails it to the client, and — when the client pays — the `checkout.session.completed` webhook reconciles the SAME `unpaid` row to `confirmed` with no duplicate. Also lands the D-02 operator status choice for no-link (cash/invoice) saves.

Purpose: Prove the D-08/D-09 no-duplicate reconciliation architecture (the phase's core landmine) on the thinnest whole-stack slice before any expansion. Every layer this phase touches is exercised on one happy path.
Output: Migration 056 (schema file), `lib/stripe-payment-links.ts`, `reconcileBookingByIdToConfirmed`, `sendPaymentRequestEmail` + `buildPaymentRequestHtml`, the extended admin POST branch, the new webhook branch, and Wave-0 test scaffolds.
</objective>

<assumption_delta_decision>
Primary noun: **booking (payment path)**.
Decision: **no-change**.
Rationale: A payment-less booking is not a new variant introduced by ANEW-05. `bookings.payment_intent_id` has always been nullable, and the existing manual POST already persists `payment_intent_id: null` with no Stripe interaction; Phase 62 added the first-class `unpaid` status for payment-pending rows. D-02 only changes the DEFAULT status of a no-link save from `pending` to an operator choice (default `confirmed`). The "booking with no payment" concept is promoted-in-place on the same noun, not added alongside a second entity. No accepted debt.
Suggested invariant test: a no-link POST always yields exactly one bookings row with `payment_intent_id IS NULL` and `payment_link_url IS NULL` (asserted in `tests/admin-bookings-payment-link.test.ts`, Plan 03).
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin browser → admin API | Authenticated operator input crosses into `POST /api/admin/bookings` (trip/client fields, collect_payment flag). |
| Stripe → webhook endpoint | Untrusted network POST to `/api/webhooks/stripe`; only a valid Stripe signature is trusted. |
| server → Stripe API | Outbound Payment Link creation; amount must be server-authoritative. |
| server → client email | Payment-request email carries client PII + a payable link; must not carry admin internals. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-64-01 | Tampering | createBookingPaymentLink amount | high | mitigate | `unit_amount` is `Math.round(booking.amount_eur*100)` — reuses the existing server recompute + `ADMIN_PRICE_TOLERANCE_CZK` gate; never a client-submitted figure. |
| T-64-02 | Spoofing/Tampering | checkout.session.completed branch | high | mitigate | Branch sits inside the existing `webhooks.constructEvent(body, sig, STRIPE_WEBHOOK_SECRET)`-verified block — inherits signature verification; a forged event is rejected before any branch runs. |
| T-64-03 | Repudiation | reconcile / duplicate delivery | medium | mitigate | `stripe_processed_events` claim (event_id unique) + status-gated `UPDATE ... WHERE status='unpaid'` (flips once; a retry matches zero rows). |
| T-64-05 | Tampering | payment-request email fields | medium | mitigate | Email fields are the already-`NO_CRLF`-validated PII from the create schema; `escapeHtml` on all interpolated values in `buildPaymentRequestHtml`. |
| T-64-06 | Information Disclosure | payment-request email / link | medium | mitigate | Email/link expose only client-facing trip + amount; never operator_notes, override rationale, or driver_price_czk (prohibition). |
| T-64-SC | Tampering | npm/pip/cargo installs | low | accept | No new package installed this phase — `stripe ^21.0.1` already present and audited (RESEARCH Package Legitimacy Audit); no install task exists. |
