Purpose: SC3 "if any hold or charge fails the client automatically gets a payment link and the operator gets an alert that does not depend on the VPS".
Output: `lib/payments/{recovery,alerts}.ts`, `createRecoveryPaymentLink`, failure wiring in hold / settle, tick steps B and D, recovery and dispute webhook handlers, tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| engine -> client email / payment link | a link that takes money from the client |
| engine -> operator email (Resend) | alerts containing client name and pickup |
| Stripe -> webhook (recovery paid) | confirmation that money arrived |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-88-42 | Tampering | recovery link amount | high | mitigate | amount = payment_amount_minor - captured_amount_minor (or the difference) from the row; link limited to one completed session; stale link deactivated before a new one |
| T-88-43 | Spoofing | recovery link routed as pay-now | high | mitigate | card_recovery kind in link and payment_intent_data metadata, no legacy booking-id key, dispatch before the legacy chain |
| T-88-44 | Repudiation | duplicate emails / alerts | medium | mitigate | ledger event keys per phase and attempt for email, alert and link |
| T-88-45 | Information disclosure | operator alert | low | accept | sent only to MANAGER_EMAIL (owner), plain text, no card data; client name and pickup needed to act |
| T-88-SC | Tampering | npm installs | low | accept | zero new dependencies (D-07) |
</threat_model>
