<objective>
Client half of 87-UAT gap 3: "Tapping Help opens a chat whose messages reach Chatwoot", keeping the call option as the fallback.

How the code settles the design (planning research, see 87-18 for the identity side):
- The trip screen lives under `app/(internal)`, whose `SiteChrome` does not mount the public `ChatLauncher`, and the `/driver` nonce CSP has no chat origin (middleware comment: "never to buildCsp()"). The public launcher cannot simply be shown there.
- The Chatwoot SDK sends `document.location.href` to the widget (`onLocationChangeListener` in the SDK's DOMHelpers, verified against chatwoot/chatwoot), which Chatwoot stores as the conversation's referer. On `/driver/trip/<token>` that would put the bearer trip token into Chatwoot. So the widget runs on a tokenless page, `/driver/trip/help` (a static segment next to `[token]`, inheriting the light driver layout), reached by a full page load so no SDK instance ever lives in the token document.
- The identity travels from the trip page to the help page in sessionStorage of the same tab (87-17 helpers), never in a URL.

Tracer: Help -> "Chat with the office" -> POST help config -> sessionStorage -> hard navigation -> `/driver/trip/help` -> `openDriverHelpChat` -> sdk.js, identified `setUser`, driver conversation attributes, widget open. Then the path-scoped CSP that lets the widget load in a real browser, then the error/fallback states, regressions and the UI-SPEC amendment.

Output: help dialog chat button, help page, driver widget opener, CSP, tests, UI-SPEC amendment B. Security-relevant (CSP and chat identity): commit with the `security:` prefix.
</objective>
