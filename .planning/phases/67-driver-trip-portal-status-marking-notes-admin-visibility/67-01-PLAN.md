<objective>
Prove the entire Phase 67 vertical end-to-end for trip-progress STATUS, on one thin
path, before any expansion: additive schema (migration 061) → live apply → a new
unauthenticated, token-gated, rate-limited driver write route → a `'use client'`
island mounted in place on the existing trip sheet → admin sees the marked progress
on booking-row expand. The isolation guarantee (DTRIP-04 / D-03 — no write to
`bookings.status`, no GNet push) is enforced structurally from the first line the
route is written.

Purpose: Trip-progress collides in vocabulary with `bookings.status` (`en_route`,
`completed` exist in both) — the ONLY thing keeping them apart is column/table
separation plus isolation-by-omission in the write route. This plan lands both and
proves them with tests + grep gates before expansion (the note, DTRIP-06) is added
in Plan 67-02.

Output: migration 061 (applied live), the write route, the client island, the admin
read surface, and the write-route test suite.
</objective>

<assumption_delta_decision>
Primary noun: `booking.status` (unchanged, client-facing source of truth).
Decision: **add-alongside** — introduce a NEW `trip_progress` vocabulary on
`driver_assignments`, parallel to `booking.status`, never merged into or promoted to
it.
Rationale: `trip_progress` is intentionally a separate, driver-only field (D-03). It
deliberately reuses the literal strings `en_route`/`completed` for driver familiarity,
which makes the isolation a structural (own column, own table) — never a conventional
— boundary. No promote is warranted; a promote would be the exact coupling DTRIP-04
forbids.
</assumption_delta_decision>
