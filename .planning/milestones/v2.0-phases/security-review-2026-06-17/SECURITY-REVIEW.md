### SEC-01: Promo code claimed before Stripe confirms payment — promo burn with no payment

**File:** `app/api/create-payment-intent/route.ts:228–239`  
**Vector:**  
1. Attacker calls `POST /api/create-payment-intent` with a valid promo code.  
2. Server atomically calls `claim_promo_code` RPC — the promo `current_uses` counter is incremented.  
3. Attacker abandons the payment (closes tab, cancels, lets the PaymentIntent expire). Payment never succeeds.  
4. Promo code is now permanently consumed with zero revenue.  
5. Repeat from multiple IPs until a limited-use code hits `max_uses` and is exhausted.

The RPC is called at line 229 immediately after price computation, but **before any payment confirmation**. The webhook (`/api/webhooks/stripe/route.ts`) does not decrement or roll back the promo counter on failed/expired PaymentIntents.

**Impact:**  
- Any limited-use promo code can be exhausted by an attacker with zero payment, destroying a marketing campaign in minutes.  
- For unlimited codes, the `current_uses` counter becomes meaningless.  
- If a promo code grants, say, 20% off and max_uses=100, an attacker burns all 100 uses at no cost.

**Fix:**  
Do NOT claim the promo at PaymentIntent creation time. Instead:
1. Validate the code at PI creation (check it's active and not exhausted) but do not increment the counter.
2. Pass the promo code in `metadata.promoCode` (already done).
3. In the `payment_intent.succeeded` webhook handler, call `claim_promo_code` there — the payment is already confirmed at that point.

```typescript
// In create-payment-intent/route.ts — REPLACE the claim block with a read-only check:
if (promoCode) {
  const supabaseService = createSupabaseServiceClient()
  const { data: promoRow } = await supabaseService
    .from('promo_codes')
    .select('discount_value, max_uses, current_uses, is_active')
    .eq('code', promoCode)
    .eq('is_active', true)
    .maybeSingle()
  if (!promoRow || (promoRow.max_uses !== null && promoRow.current_uses >= promoRow.max_uses)) {
    return NextResponse.json({ error: 'Promo code is invalid or exhausted.' }, { status: 400 })
  }
  appliedPromoPct = Number(promoRow.discount_value)
}

// In webhooks/stripe/route.ts handleOneWaySucceeded / handleRoundTripSucceeded:
// After confirmed DB insert, call claim_promo_code(meta.promoCode) if present.
```

### SEC-02: `/api/driver/respond` has no rate limit — driver token brute-forceable

**File:** `app/api/driver/respond/route.ts:11`  
**Vector:**  
The endpoint accepts a `token` field validated as a UUID (`z.string().uuid()`). A UUID has 2^122 possible values in the v4 space, which is theoretically large — but the attack surface is:

1. The token is generated by the DB (presumably `gen_random_uuid()`). UUIDs are not cryptographic secrets; their entropy is 122 bits of randomness.  
2. **No rate limit is applied to this endpoint.** There is no `checkRateLimit` call anywhere in `app/api/driver/respond/route.ts`.  
3. There is no CSRF guard (not in `CSRF_PROTECTED_PREFIXES`).  
4. The endpoint is POST, public, and returns distinguishable responses: `{ error: 'not_found' }` vs `{ error: 'used' }` vs `{ error: 'expired' }` vs `{ ok: true }`.

An attacker can spam this endpoint at full serverless throughput (thousands of req/s) with no throttling. While brute-forcing 122-bit UUIDs is impractical computationally, the absence of rate limiting means:
- A valid token intercepted from an email link (e.g. via phishing the driver, email replay, or a logged URL) can be used without limit.
- Any future vulnerability that narrows token search space (e.g. predictable seeds, sequential IDs, info leak) would have no rate-limit backstop.
- The endpoint also leaks whether a token ever existed (`not_found` vs `expired`/`used`), enabling oracle-style probing.

**Impact:** Driver assignments can be accepted or declined by an unauthorized party. An attacker who intercepts one driver email link can replay it to accept/decline booking assignments, disrupting operations.

**Fix:**
```typescript
// app/api/driver/respond/route.ts — add at the top of POST():
import { checkRateLimit, getClientIp } from '@/lib/rate-limit'
// In LIMITS in rate-limit.ts:
// '/api/driver/respond': 10,

const { allowed } = await checkRateLimit('/api/driver/respond', getClientIp(request))
if (!allowed) {
  return NextResponse.json({ error: 'Too many requests' }, { status: 429 })
}
```
Also normalize error responses to not distinguish `not_found` from `expired` to prevent oracle enumeration.

### SEC-03: `bookings` RLS SELECT policy allows authenticated users to read ALL bookings when `user_id IS NULL`

**File:** `supabase/migrations/049_bookings_customer_rls.sql:13–14`  
**Vector:**

```sql
CREATE POLICY bookings_select_own
  ON public.bookings FOR SELECT
  TO authenticated
  USING (user_id = (select auth.uid()));
```

This policy correctly restricts rows WHERE `user_id` matches. However, in PostgreSQL RLS, `NULL = anything` evaluates to `NULL`, not `TRUE` or `FALSE`. A `USING` clause that evaluates to `NULL` is treated the same as `FALSE` — the row is hidden. So NULL rows are already hidden.

**But the actual problem is the opposite direction:** Any authenticated user (any logged-in customer, not just admin) querying the `bookings` table with the anon/authenticated key CAN only see their own `user_id`-linked rows. Guest bookings (user_id = NULL) are correctly hidden.

Wait — re-examining the `/account/trips/page.tsx:33-35`:

```typescript
const { data: bookings } = await supabase
  .from('bookings')
  .select('...')
  .order('pickup_date', { ascending: false })
  .limit(50)
```

The server component uses `createClient()` (anon key + user session cookie). The RLS policy will filter to only that user's bookings — **this is correct**.

However: the `bookings` table was created WITHOUT RLS in earlier migrations (pre-049). Migration 049 does `ALTER TABLE public.bookings ENABLE ROW LEVEL SECURITY` — but only defines a SELECT policy for authenticated users. **There is NO policy defined for the `anon` role.** In Supabase, when RLS is enabled with no matching policy, the default is DENY for that role. This means anon (unauthenticated) users cannot SELECT — correct.

**The real finding:** The `bookings` table has RLS enabled for SELECT only (migration 049). There are **no INSERT, UPDATE, DELETE policies** for any customer role. All writes go through `service_role` (webhook, API routes) — which bypasses RLS by default. This is intentional per the migration comment.

**Revised actual vulnerability:** The `bookings_select_own` policy uses `user_id = (select auth.uid())`. For an authenticated user where `auth.uid()` returns a valid UUID, rows with `user_id = NULL` evaluate to `NULL` (hidden) — correct. **BUT:** if the Supabase anon key is used client-side (e.g., via `createBrowserClient` in booking-store or a direct fetch), and if a developer accidentally calls `.from('bookings').select()` from client-side code with an authenticated session, the RLS policy will still protect them.

**Real gap that IS exploitable:** The trips page query has NO `.eq('user_id', user.id)` filter — it relies entirely on RLS. If RLS is ever accidentally disabled (e.g., via a future migration that does `ALTER TABLE bookings DISABLE ROW LEVEL SECURITY` without noticing), ALL bookings become visible to any authenticated user with no application-layer guard.

**Fix:** Add a defense-in-depth filter even though RLS is active:
```typescript
// app/account/trips/page.tsx
const { data: bookings } = await supabase
  .from('bookings')
  .select('...')
  .eq('user_id', user.id)  // Add this — defense-in-depth on top of RLS
  .order('pickup_date', { ascending: false })
  .limit(50)
```

### SEC-04: `getSession()` used in Step3Auth component — stale session trust

**File:** `components/booking/steps/Step3Auth.tsx:134`

```typescript
supabase.auth.getSession().then(({ data: { session } }) => {
  if (session) {
    ...
    nextStep()
  }
})
```

`getSession()` on the browser client reads the session from local storage without re-validating the JWT with the Supabase auth server. This means:
- A revoked or expired (but locally cached) session will still pass this check.
- A user who has been banned or had their account deleted will still auto-advance through the booking wizard.

The Supabase documentation explicitly warns: "Always use `getUser()` server-side. On the browser, `getSession()` is acceptable for UI purposes but not for security gating."

**Impact:** A user whose account has been revoked or deleted from Supabase Admin can still complete a booking as an authenticated user if their local session token hasn't expired. The `userId` stored in Stripe metadata would reference a deleted user.

**Fix:**
```typescript
// Replace getSession() with getUser() in Step3Auth.tsx useEffect:
supabase.auth.getUser().then(({ data: { user } }) => {
  if (user) {
    sessionStorage.removeItem('booking_deeplink')
    if (sessionStorage.getItem('oauth_login_pending') === '1') {
      sessionStorage.removeItem('oauth_login_pending')
      window.gtag?.('event', 'login', { method: 'oauth' })
    }
    setGuestMode(false)
    nextStep()
  }
})
```

### SEC-05: `/api/driver/respond` not in CSRF_PROTECTED_PREFIXES — CSRF-vulnerable

**File:** `middleware.ts:7–13`

The CSRF protection list:
```typescript
const CSRF_PROTECTED_PREFIXES = [
  '/api/admin',
  '/api/submit-quote',
  '/api/contact',
  '/api/create-payment-intent',
  '/api/calculate-price',
]
```

`/api/driver/respond` is a POST endpoint that changes booking assignment status (accept/decline). It is NOT in this list. A CSRF attack against a driver:

1. Attacker crafts a page: `<form action="https://rideprestigo.com/api/driver/respond" method="POST">` with a valid token embedded (obtained via phishing the driver).
2. Driver visits attacker's page while having a valid session (not required for this endpoint, but the token provides the auth).
3. The form auto-submits, silently accepting or declining a booking assignment.

Since the endpoint authenticates purely via the `token` body field (not via cookie), the CSRF risk is somewhat mitigated — an attacker needs the token. But combined with SEC-02 (no rate limiting), a CSRF + token-guessing attack becomes plausible.

**Impact:** Booking assignments can be silently accepted or declined by tricking a driver into visiting a crafted page.

**Fix:** Add `/api/driver/respond` to `CSRF_PROTECTED_PREFIXES`.

### SEC-06: `NEXT_PUBLIC_META_PIXEL_ID` exposed in CAPI route — pixel ID enumerable from client

**File:** `app/api/meta-capi/route.ts:5`

```typescript
const PIXEL_ID = process.env.NEXT_PUBLIC_META_PIXEL_ID
```

Using `NEXT_PUBLIC_` prefix means this value is bundled into the client-side JavaScript bundle and is publicly visible. While the Pixel ID itself is not a secret (it appears in the browser's network traffic and page source anyway), using it server-side in the CAPI route creates a subtle confusion: if someone rotates the Pixel ID for security reasons, the `NEXT_PUBLIC_` value in the bundle may be stale/cached, while the server-side code reads the same value.

More importantly: if the intent was to keep the Pixel ID non-public (some operators prefer to obscure their analytics config), using `NEXT_PUBLIC_` defeats this.

**Impact:** Low in isolation. The CAPI access token (`META_CAPI_TOKEN`) is correctly using a non-prefixed env var. The Pixel ID exposure only reveals which Meta Pixel is in use.

**Fix:** If pixel ID needs to be used only server-side (CAPI), rename to `META_PIXEL_ID` without the `NEXT_PUBLIC_` prefix. The client-side fbq() call already has the pixel ID baked in via the GTM snippet, so server-side usage doesn't need the public prefix.

### SEC-07: `custom_data` object passed through unvalidated to Meta CAPI

**File:** `app/api/meta-capi/route.ts:90–92`

```typescript
if (body.custom_data && typeof body.custom_data === 'object') {
  event['custom_data'] = body.custom_data
}
```

The `custom_data` field is forwarded to Meta's Graph API with only a typeof check. No Zod validation, no field allow-listing, no depth/size limit. An attacker can:
1. POST to `/api/meta-capi` with an arbitrarily large or deeply nested `custom_data` object.
2. This object is forwarded directly to `https://graph.facebook.com/v19.0/.../events`.
3. Could be used to inject unexpected event data into the Meta analytics pipeline, or to attempt server-side request amplification (send large payloads to Meta at Prestigo's API rate limit cost).

The 8KB body limit (`enforceMaxBody(request, 8_000)`) provides some protection, but the content of `custom_data` is not validated.

**Impact:** Potential analytics poisoning, unexpected Meta API costs, or amplified requests to Meta's servers on behalf of the server.

**Fix:**
```typescript
// Add Zod schema for custom_data
const customDataSchema = z.object({
  value: z.number().optional(),
  currency: z.string().max(3).optional(),
  content_name: z.string().max(200).optional(),
  content_category: z.string().max(200).optional(),
}).strict()

// Replace the passthrough:
const customDataParsed = customDataSchema.safeParse(body.custom_data)
if (customDataParsed.success) {
  event['custom_data'] = customDataParsed.data
}
```

### SEC-08: `/api/submit-quote` reveals full Zod validation error details to client

**File:** `app/api/submit-quote/route.ts:70–73`

```typescript
return NextResponse.json(
  { error: 'Invalid request', details: parsed.error.flatten() },
  { status: 400 }
)
```

`parsed.error.flatten()` returns the full Zod field-level error tree, including field names and constraint details. This is an information disclosure:
- Reveals internal field names and schema structure
- Useful for attackers to probe the validation logic
- Can reveal whether specific fields exist (e.g. an attacker learns the schema has a `passengerDetails.specialRequests` field with a 1000-char limit)

**Impact:** Medium. Enables schema enumeration. Consistent with the `/api/admin/bookings` PATCH route which also exposes `parsed.error.issues` — the pattern is widespread.

**Fix:** In production, return only a generic error:
```typescript
return NextResponse.json(
  { error: 'Invalid request' },
  { status: 400 }
)
```
Or gate detailed errors on `process.env.NODE_ENV === 'development'`.

### SEC-09: GNet farmin route allows `UPDATE` to overwrite booking with attacker-controlled data

**File:** `app/api/gnet/farmin/route.ts:347–397`

The UPDATE branch finds an existing booking by `transaction_id` and replaces passenger data (name, email, phone) and trip details with data from the incoming payload:

```typescript
client_first_name: firstPassenger?.firstName ?? 'GNet',
client_last_name:  firstPassenger?.lastName ?? 'Partner',
client_email:      firstPassenger?.email || 'noreply@gnet.local',
client_phone:      firstPassenger?.phoneNumber || 'unknown',
```

The `GnetPassengerSchema` allows all passenger fields as optional strings with `.passthrough()` — no max-length, no format validation:

```typescript
const GnetPassengerSchema = z.object({
  firstName:   z.string().optional(),
  lastName:    z.string().optional(),
  email:       z.string().optional(),
  phoneNumber: z.string().optional(),
}).passthrough()
```

If the GNet Basic Auth credentials are compromised (or if a GNet partner sends a malformed UPDATE), an attacker can overwrite the passenger name, email, and phone on an existing confirmed booking to arbitrary values — including SMTP header injection sequences (`\r\n`), XSS payloads (if the admin UI renders them unescaped), or simply wrong contact details that cause operational failure.

**Impact:** Booking data corruption, potential SMTP header injection via the email field in subsequent reminder emails.

**Fix:**
```typescript
const GnetPassengerSchema = z.object({
  firstName:   z.string().max(100).regex(/^[^\r\n]*$/).optional(),
  lastName:    z.string().max(100).regex(/^[^\r\n]*$/).optional(),
  email:       z.string().email().max(200).regex(/^[^\r\n]*$/).optional(),
  phoneNumber: z.string().max(30).regex(/^[^\r\n]*$/).optional(),
})
// Remove .passthrough() from GnetPassengerSchema
```

### SEC-10: Stripe webhook `stripe_processed_events` idempotency gate has a TOCTOU gap

**File:** `app/api/webhooks/stripe/route.ts:66–81`

The webhook inserts into `stripe_processed_events` to claim the event. If the INSERT fails with a non-23505 error (line 78), it returns 500, causing Stripe to retry. On retry, the insert may succeed — but the original handler may have already partially processed the event (e.g. `saveBooking` succeeded but email sending failed). The retry will then be blocked by the 23505 check — but emails won't be resent.

More critically: there is a window between the `stripe_processed_events` INSERT succeeding (line 67) and the downstream booking insert (`saveBooking`) being called (line 138 in `handleOneWaySucceeded`). If the process crashes between these two operations:
- The event is marked as processed in `stripe_processed_events`
- The booking row was never created
- Stripe retries → 23505 → `{ received: true, duplicate: true }` → Stripe stops retrying
- **Booking is lost with no alert**

The `sendEmergencyAlert` is only called when `saveBooking` itself throws after 3 retries — it's not called when the process dies between the idempotency insert and the save.

**Impact:** In a crash/OOM scenario (rare but real on serverless), a completed payment can result in no booking record and no alert. Revenue is collected but no service is dispatched.

**Fix:** Reverse the order — do the booking DB write FIRST, then mark the event as processed. Or use a two-phase approach: mark the event as "in-progress" first, then "completed" after the full handler runs. Alternatively, implement a reconciliation job that detects PaymentIntents with no corresponding booking row.

### SEC-11: Admin layout uses `getUser()` correctly but individual API routes re-implement auth independently — inconsistent guard patterns

**Files:** `app/admin/(dashboard)/layout.tsx`, multiple `app/api/admin/*/route.ts`

The admin layout correctly uses `getUser()` + `app_metadata.is_admin` check. Each API route independently defines its own `getAdminUser()` helper. Several routes import it from different locations:
- `app/api/admin/bookings/route.ts` defines its own `getAdminUser()` locally
- `app/api/admin/bookings/[id]/assign/route.ts` imports from `@/lib/supabase/server`
- `app/api/admin/bookings/cancel/route.ts` defines its own local `getAdminUser()`

If a future change modifies the auth logic in one place (e.g. adds 2FA check, IP allowlist), it may not propagate to all copies. The layout-level auth guard doesn't protect API routes (API routes are not protected by layout Server Components).

**Impact:** Maintenance risk. A future weakened auth check in one copy leaves the corresponding API route exposed.

**Fix:** Consolidate to a single exported `getAdminUser()` from `@/lib/supabase/server` and remove all local copies.

### SEC-12: `/api/validate-promo` discloses promo code existence via timing differential

**File:** `app/api/validate-promo/route.ts:21–43`

The endpoint makes a DB query for each code lookup. Valid codes (found in DB) take slightly longer than invalid codes (quick DB miss). More importantly, the response distinguishes:
- `{ valid: false, error: 'Code not found, expired, or inactive.' }` — code doesn't exist or is inactive
- `{ valid: false, error: 'This promo code has reached its usage limit.' }` — code exists but exhausted

An attacker can distinguish active codes from exhausted ones, and both from non-existent ones. Combined with the 20-request/minute rate limit, this provides an enumeration oracle.

**Impact:** Promo code enumeration is possible with 20 guesses/minute/IP. At typical 6-character alphanumeric codes this is slow but possible given unlimited time.

**Fix:** Return a uniform error message regardless of the reason for failure:
```typescript
return NextResponse.json({ valid: false, error: 'Invalid or unavailable code.' })
```

### SEC-13: `pickupDate`/`pickupTime` 12-hour advance check is timezone-naive

**Files:** `app/api/create-payment-intent/route.ts:153–162`, `app/api/submit-quote/route.ts:78–85`

```typescript
const pickupDT = new Date(`${bookingData.pickupDate}T${bookingData.pickupTime}:00`)
```

This constructs a Date with no timezone — JavaScript interprets it as LOCAL server time (UTC in production, but local in development). A customer booking a Prague pickup at "23:00" on "2026-06-20" sends the string `2026-06-20T23:00`. If the server is in UTC and the customer is in CEST (UTC+2), the actual pickup is at 21:00 UTC — but the server validates against 23:00 UTC, accepting a booking that's effectively 2 hours earlier than the validation threshold.

**Impact:** Bookings can be placed less than 12 hours before pickup if the client timezone is ahead of server UTC. In edge cases, a booking 10 hours before pickup could pass the 12-hour check.

**Fix:** Store and compute pickup times in UTC with explicit timezone. Require the client to send an ISO 8601 string with timezone offset, or document that all times are in Prague local time (CET/CEST) and normalize server-side with a known offset.

### SEC-14: `CRON_SECRET` comparison is constant-time but `TELEGRAM_WEBHOOK_SECRET` comparison is not

**Files:** `app/api/cron/reminder-24h/route.ts:12–14`, `app/api/telegram/webhook/route.ts:32–35`

The cron endpoint:
```typescript
if (!process.env.CRON_SECRET || authHeader !== `Bearer ${process.env.CRON_SECRET}`) {
```

The Telegram webhook:
```typescript
if (!expected || got !== expected) {
```

Both use JavaScript's `!==` operator for string comparison — this is a timing-safe comparison in modern V8 (strings are compared bytewise and the comparison exits early on mismatch), but the official guidance for secrets is to use `timingSafeEqual`. The GNet farmin endpoint correctly uses `timingSafeEqual` — the cron and Telegram endpoints should follow the same pattern.

**Impact:** Theoretical timing side-channel to brute-force these secrets. Low practical risk in HTTP context due to network jitter, but the inconsistency signals an incomplete security pattern.

**Fix:** Use `timingSafeEqual` as done in the GNet farmin route for all secret comparisons.

### SEC-15: `bookingData.quoteMode === 'true'` string comparison bypass for round_trip

**File:** `app/api/create-payment-intent/route.ts:147–149`

```typescript
if (bookingData.quoteMode === 'true') {
  return NextResponse.json({ error: 'This route requires a custom quote.' }, { status: 400 })
}
```

This check is intended to prevent round-trip bookings where the distance is in "quote mode" from being charged. The Zod schema allows `quoteMode: z.string().max(10).optional()` via the catchall — meaning the client can simply omit `quoteMode` (undefined) or send `'false'` to bypass this check. The check only fires on the explicit string `'true'`, not on boolean `true`.

While the server-side pricing computation (`computeOutboundLegTotal`) likely handles this correctly regardless, the intent of this guard appears to be a business rule: "don't let clients pay for quote-mode trips." If the pricing function returns a valid price for a route the operator intended to quote-only, the check is the only gate.

**Impact:** Medium. If an operator marks a route as `quoteMode: true` on the client but the server price computation still produces a valid number, the check can be bypassed by omitting `quoteMode` from the request.

**Fix:** Treat absence of quoteMode as 'false', but validate the actual trip data server-side rather than relying on a client-supplied quoteMode flag. Or make quoteMode a server-side computed property based on distance thresholds configured in admin.

### SEC-16: `bookingData` is double-asserted to `Record<string, string>` losing Zod type safety

**File:** `app/api/create-payment-intent/route.ts:96`

```typescript
const { bookingData } = parsed.data as { bookingData: Record<string, string> }
```

The Zod schema uses `.catchall(BOUNDED_STRING)` but the top-level type is `z.object({ bookingData: z.object({...}).catchall(...) })`. Casting to `Record<string, string>` after parsing discards TypeScript's knowledge that certain fields (like `tripType`, `vehicleClass`) are already validated as enums. This is a type-safety regression that could mask future bugs where typed fields are accidentally treated as raw strings.

**Fix:** Use `parsed.data.bookingData` directly with the inferred Zod type rather than casting.

### SEC-17: Content-Security-Policy for `/book` uses `unsafe-inline` — weakens XSS protection for payment pages

**File:** `middleware.ts:178–185`

The `/book` route (including Step6Payment where Stripe Elements render) uses `buildCspStatic()` which includes `"script-src 'unsafe-inline' https:"`. This means any injected `<script>` tag on the booking page would execute, undermining the XSS protection entirely. The justification in comments is analytics compatibility, but the trade-off directly affects the page where payment card data is entered (though Stripe isolates this in an iframe).

**Fix (hardening, not immediate):** Split analytics scripts to a separate layout group that reads the nonce from headers, enabling strict nonce-CSP on `/book`.
