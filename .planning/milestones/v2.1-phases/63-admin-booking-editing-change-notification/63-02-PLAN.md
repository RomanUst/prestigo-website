## Planner Assumptions (spec-less edge probe — surfaced, not dropped)

The phase has no plain SPEC; the edge probe returned 11 unresolved edges. Those covered by an `auto`-resolvable acceptance criterion are lifted into `must_haves.truths` above. The remainder are surfaced here as explicit flagged assumptions for this plan's requirements (AEDIT-01, AEDIT-04, AEDIT-05):

- **[ASSUMPTION] AEDIT-01 (unclassified):** pickup date/time is treated as a cheap direct-commit field pair with no boundary beyond the `^\d{4}-\d{2}-\d{2}$` / `^\d{2}:\d{2}$` regex — no server-side "pickup must be in the future" gate is added this phase (operators legitimately backdate/correct). If a future-date guard is wanted, it is out of this phase's scope.
- **[ASSUMPTION] AEDIT-04 (precision):** passenger/contact/flight fields have no numeric-precision axis; the only boundaries are the schema max-lengths (name 100, email 200, phone 50, flight 20) + `NO_CRLF`. No further normalization (trimming, case-folding) is applied.
- **[ASSUMPTION] AEDIT-05 (concurrency) — REAL GAP, flagged:** two operators editing the same booking concurrently is last-write-wins on the `bookings` row; the audit log is append-only so no audit history is lost, and `logEmail`'s dedup window prevents a duplicate change email. No row-level lock / optimistic-concurrency token is added this phase. If concurrent-edit protection is required, it is a follow-up.
