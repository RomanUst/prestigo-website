<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin browser -> PATCH API (Plan 02 consumer) | Operator-supplied field values (name/email/flight/addresses) will flow into the change email built here — untrusted content crosses into an outbound email. |
| API -> Resend | Rendered HTML (incl. old/new values) is sent to a third party for delivery to the client. |
| API -> Supabase (new table) | Service-role-only writes/reads of the audit log. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-63-01-01 | Tampering / Injection | buildChangeEmailHtml old/new values | high | mitigate | escapeHtml applied to every label/oldValue/newValue before interpolation (Task 2 behavior + acceptance grep); mirrors the escapeHtml-everything discipline of buildStatusEmailHtml. |
| T-63-01-02 | Information Disclosure | change email content (D-07) | medium | mitigate | Email renders only the changed fields, never a full trip/PII snapshot — reduces accidental over-disclosure. |
| T-63-01-03 | Tampering | booking_edit_audit_log write path | low | accept | Service-role-only table (no RLS); only the admin-guarded API writes/reads it. RLS deferred, mirroring email_log — same posture as existing tables. |
</threat_model>
