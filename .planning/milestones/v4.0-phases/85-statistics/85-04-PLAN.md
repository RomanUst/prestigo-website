- main (only when run directly): read stdin, loadChatwootConfig(), createChatwootClient(...), runBackfill with process.stdout/stderr; exit 0 on success, 2 on config/input error (message without any secret).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Chatwoot API -> backfill script -> SQL text | conversation payloads are external data that end up in SQL the orchestrator executes |
| owner token file -> script | the Chatwoot API token must never leave the owner's machine or appear in output |
| Chatwoot webhook -> intake -> reserveLead | the channel string comes from a verified webhook payload |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-85-13 | Tampering | SQL injection through a crafted meta.channel or lead id in the backfill output | high | mitigate | strict regexes before building a statement (channelOf, backfillStatement, parseBackfillInput); unit test with a quote-injection value; orchestrator re-checks every line against the exact UPDATE regex before applying |
| T-85-14 | Information Disclosure | API token or contact PII printed by the script | high | mitigate | token only via loadChatwootConfig, never argv/printed; output is SQL, ids, HTTP statuses and counts; test asserts sender name/email and token are absent |
| T-85-15 | Tampering | script mutating Chatwoot data | medium | mitigate | GET-only (grep acceptance + every fake fetch call asserted GET) |
| T-85-16 | Tampering | unbounded channel text from the webhook stored in chat_leads | low | mitigate | raw value bucketed by SQL to five literals and enforced by the 081 CHECK |
